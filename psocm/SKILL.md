# PSOCM 论文分析

以 AI 系统领域专家的视角，严格依据目标论文及核实过的学术文献进行系统性分析。默认使用中文，保留论文术语、系统名和论文完整原标题。先说清问题，再解释证据与设计逻辑；避免空泛背景、推测、补全和泛化总结。

## 材料与证据

1. 在 Sanctuary 中先查找已有论文笔记、相关主题和原文，读取对应笔记及 YAML 并沿 `source` 阅读原文。用户直接提供的论文以原文为依据；已有索引与笔记只用于导航。
2. 阅读目标论文的问题定义、相关工作、动机、设计与实验，按需核对附录。PDF 提取存在公式、图表或排版缺失时，检查对应页面图像。只有摘要或部分原文时，明确分析覆盖范围，不补齐未读部分。
3. 用目标论文参考文献定位相关工作，必要时检索出版方、会议官网、作者论文或预印本等一手来源。纳入二维分类前核实其研究场景与方法；只有目标论文的转述时，注明“据目标论文对该工作的描述”，不要写成独立核验结论。
4. 问题定义、分类依据、limitations、insights、设计与关键实验结论均给出可回查位置，例如“§3.2，Fig. 4，PDF 第 5 页”；区分 PDF 页码与印刷页码。外部文献附论文页或 DOI 等可靠链接。数值须交代指标、基线和关键实验条件，不把局部结果泛化。
5. 区分“作者明确陈述”“依据原文重组的分析”和“证据不足”。重组仅改变论述组织，不引入原文未支持的机制、因果或结论。无法核实时写“原文未说明”“未发现相应证据”或“尚未核实”，不要猜测。
6. SoTA 指目标论文研究时的相关工作语境；若用户要求当前最新进展，另行检索并明确区分后续工作，不能用后来发表的成果倒推原论文的新颖性。

默认在对话中输出分析。仅在用户要求保存、更新笔记或入库时修改知识库文件，并遵守项目 `AGENTS.md` 和 `paper-intake` 的命名、YAML、日记记录和个人笔记保留规则；不自动把已有短笔记改成长篇分析。

## 输出结构

严格按以下六部分组织。正文以证据充分为准，不为填满结构而编造两条发现或额外模块。编号统一使用 L1/L2、O1/O2、C1/C2、M1/M2。

## 1. Problem

### Problem Statement

从聚焦的系统场景说明研究背景：系统服务谁、运行在哪里、执行何种工作负载，以及与研究问题直接相关的条件或约束。避免只说“AI 发展迅速”“LLM 应用广泛”。

接着明确：在这个场景下，本文究竟要解决什么主要问题。按原文说明研究范围和目标，不将所用方法当作问题本身。

### Input

把整篇论文视作一个系统，用最多 **4 条 bullet** 列出系统需要输入的信息。区分实际输入、运行环境与优化目标，不把论文没有使用的信息列为输入。

### Output

说明系统输出的具体对象，如调度方案、执行计划、资源分配、推理结果或训练后的模型；以原文为准。“提高效率”“降低延迟”是目标或效果，不是输出对象。

### Significance

解释为什么该问题值得研究：受影响的系统能力、现有瓶颈及其实际后果。依照作者的论证和证据，不替作者追加产业价值或未经验证的普遍意义。

## 2. SoTA & Limitations

### Related Works：场景 × 技术九宫格

先界定分类所覆盖的研究问题和文献范围。在此范围内提炼两个维度，每个维度恰分两类：

- **场景维度（行）**回答已有工作主要在什么应用或系统场景研究该问题。B1 是与本文场景有关键差别的类别；B2 是本文聚焦的场景类别。
- **技术维度（列）**回答已有工作用什么方法范式解决该问题。A1 是其他方法类别；A2 是本文采用的方法类别。

为 A1、A2、B1、B2 起有实质含义的名称，说明分类标准与边界。技术类别不能只是系统名，也不能把场景属性换个名字充当技术维度。尽可能覆盖选定范围的相关工作，类别尽量互斥、边界清晰；跨界工作须解释归类依据，无法合理二分时说明分类限制，不硬塞。

使用含表头的 **3×3 表格**：左上角写整体研究问题，四个内容格列论文。示意结构如下；实际输出替换为具体类别与已核实论文：

| 整体研究问题 | A1：技术类别 | A2：技术类别 |
|---|---|---|
| B1：其他场景类别 | A1–B1 工作 | A2–B1 工作 |
| B2：本文场景类别 | A1–B2 工作 | 本文（Ours），并如实列出同类已有工作 |

四个内容格中用简短 bullet 表示论文，格式为 `- [NSDI'26] Agentix`，不写完整标题。单元格内多条可用 `<br>` 换行。使用论文已有简称或可辨识短标题，不编造官方系统名；未知会议信息不得猜测，预印本如实标注为 arXiv。

在表格下列出表中**所有论文，包括本文**的会议、年份和完整标题，并附核实来源，例如：

- [NSDI'26] Agentix: An Efficient Serving Engine for LLM Agents as General Programs

例子只展示格式，不要求把 Agentix 纳入任何实际分析。

明确写出“本文位于 **B2 场景类别 × A2 技术类别** 的交叉点”，并依据原文解释该交叉点为何尚未充分研究。目标是检验本文能否唯一落在右下角；若已有工作也在此处，必须如实保留并解释差异，不能通过改分类、删文献或宣称空白来制造唯一性。未检索到同类论文不等于证明不存在。

### L1：场景维度的 Limitation

从 **A1–B1 与 A2–B1** 提炼场景层面的结构性共性问题：它们的场景前提、任务特征或系统假设为何无法覆盖 B2 的关键要求。说明适用范围及原文依据，不能把研究范围不同直接写成方法本身无效。

### L2：技术维度的 Limitation

从 **A1–B2** 提炼技术层面的结构性共性问题：即使进入本文场景，现有方法范式为什么仍有共同限制。说明限制来自什么机制或假设，不能仅罗列各系统的零散缺点。

L1 与 L2 应分别对应两个维度，且能够自然导向后续机会与设计。如果某组工作没有证据，或原文不足以支持共同 limitation，保留该编号并注明证据缺口，不虚构共性。

## 3. Opportunity & Insight & Motivation

先判断论文实际采用的 motivation pattern，可单独或组合使用：

- **Observation-driven**：来自 preliminary experiments、case studies 或经验观察。
- **Assumption-breakdown driven**：现有方法的关键假设在新场景下失效。
- 其他原文明确支持的模式：说明具体来源及为何适合本文。

不要默认 opportunity 必须来自预实验。先提取论文支持的 insight，再判断作者用什么证据支撑；有预实验时说明实验如何支持该 insight，没有时明确写“未提供对应预实验”，说明作者实际使用的论证。不得自行设计实验并写成论文事实，也不能把最终性能评估冒充 preliminary experiment。

### O1 → L1

围绕解决 L1 的新支点，依次输出：

1. **Motivation source**：具体观察、假设失效或其他新支点是什么；提炼对应 insight，并给出来源。有实验时交代设置、对照、指标、观察和支持范围。
2. **Why existing SoTA could not exploit it**：现有方法为什么未能利用该支点；只陈述原文支持的机制或限制，不猜测研究者意图。
3. **Why it now opens a new research direction**：什么场景特征、可用信息、系统条件或已验证性质使其能够支撑新路线。
4. **Opportunity statement**：凝练为一句 research opportunity，明确它如何回应 L1。
5. **Bridge to challenge**：该机会虽有潜力，但实现时还面临什么技术困难，从而引出 C1。

### O2 → L2

沿用以上五项，回应 L2，并引出 C2。两项机会应有可区分的逻辑，不把同一 insight 换词重复。

Opportunity 提供新支点，**不是方法设计**：此处不提前展开本文的 model、module 或 framework。若原文仅支持一个机会，明确第二条无法独立提炼。

### C2 → O2

每项 challenge 写成明确研究问题，例如“如何建模……”“如何统一……”“如何优化……”，随后说明实现对应 opportunity 时的技术障碍、相互制约的目标或必须处理的条件，并给出原文位置。

Challenge 是**机会落地时的技术难题**，不能只是重述 limitation，也不能把最终模块名称改写为问句。若挑战来自对设计段落的重组，注明“依据设计论述归纳”，不冒充作者明确列出的挑战。

## 5. Model

### M1 → C1

### M2 → C2

Model 在此包括论文实际提出的模型、算法、机制或系统模块，不强制解释为机器学习模型。对每项设计说明：

- **目标与对应挑战**：解决 C1/C2 的哪一项具体困难。
- **核心思想**：输入、关键机制和输出；必要时使用原文公式，并解释变量与前提。
- **设计依据**：什么 insight 或系统性质支撑该设计，为什么该机制能回应挑战；不得添加原文没有的理论保证。
- **证据与边界**：原文设计位置、适用条件，以及有无直接实验支持。整体加速结果不能直接证明某模块的独立贡献；只有相应消融或其他证据才能如此归因。

忠实描述已有设计，不替论文提出新方案。M1/M2 是解释上的对应关系，不强行把一个耦合机制拆成两个独立模块；模块共同解决挑战时明确共同作用。若原文确有必要的第三项设计，可列 **M3 → C1 和/或 C2**，解释 M1/M2 为何不足及 M3 的职责，不为了结构对称新增模块或挑战。

最后说明模块如何组成完整框架：数据流、执行顺序、关键交互，以及如何从系统输入得到输出。只画原文支持的流程。

## 6. Contributions

将原文支持的贡献归纳为三类，区分作者声称的新颖性与本文实际给出的验证：

- **Conceptually**：新问题、新场景组合、新视角或新范式；避免无证据的“首次”。
- **Technically**：实际提出的新模型、机制或系统设计，说明对应挑战及技术增量。
- **Experimentally**：实验验证、性能效果、适用范围或 benchmark 贡献，交代基线、条件和限制；没有 benchmark 贡献时不添加。

某类没有独立贡献时直接说明，不将实现细节包装为概念贡献，也不将实验覆盖外的场景写成已验证能力。

## 完成前核对

- 六部分齐全；Input 不超过 4 条；Output 为具体对象。
- 九宫格行列、分类说明和 L1/L2 一致；表内简称与表下完整标题一一对应；没有为唯一性歪曲已有工作。
- `L1 → O1 → C1 → M1` 与 `L2 → O2 → C2 → M2` 的逻辑可追溯；缺失环节如实标注，联合设计如实说明。
- 清楚区分 preliminary evidence、设计依据、最终评估与个人归纳；没有虚构实验、文献、公式、模块或用户阅读感受。
- 重要论断有原文位置或可靠一手来源；结论没有超过证据支持范围。
